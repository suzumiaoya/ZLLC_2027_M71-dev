## CAN 地址与同总线约束

实机使用 `CAN_ID = 0x301`～`0x308` 通信失败，新配置使用 `0x01`～`0x08`。以下范围按尾号 1～8 计算，均为同一条物理 CAN 总线上的标准帧 ID。

| 报文 | 新配置 | 旧配置 |
|---|---|---|
| MIT（含 MCU 侧 MIT 速度环） | `0x01`～`0x08` | `0xF1`～`0xF8` |
| 位置速度 | `0x101`～`0x108` | `0x1F1`～`0x1F8` |
| 驱动器速度模式 | `0x201`～`0x208` | `0x2F1`～`0x2F8` |
| 电机反馈 | `MST_ID`，本次配置为 `0x11`～`0x18` | 由上位机指定，已有配置可继续使用 |

- **达妙使用驱动器速度模式时，禁止与大疆电机共用一条 CAN 总线。** 新配置的速度命令与大疆电机反馈 `0x201`～`0x208` 重叠。改 `MST_ID` 或配置 MCU 接收过滤器都无法消除线上重号。Alive 的使能和失能帧也使用当前模式地址。
- `MST_ID = 0x10 + l` 与表中所有达妙控制地址、常规大疆电机控制和反馈地址均无交集。此结论限于上述设备和地址。同总线各电机的 `MST_ID` 应唯一，且须避开其他设备的收发地址。工程里的达妙 IMU 配置示例使用 `0x01` 和 `0x11`，与尾号 1 的 MIT 和反馈地址均重叠；即使 MCU 的 IMU 回调被注释，接在线上的 IMU 仍可能使用这些地址。
- 应用按总线和上位机实际设置的 `MST_ID` 分发反馈。现有云台回调使用 `0xA1`、`0xA2`，仅修改上位机不能让原回调收到 `0x11`、`0x12`。若使用固定 ID 的集中发送，也须核对调度处的发送地址。
- 同总线的新旧达妙配置共用尾号对应的发送缓冲区，例如 `0x01` 与 `0xF1` 不可同时分配。不同物理总线可复用相同地址。

## 2. 问题

达妙反馈帧第一字节 `D[0] = ID | (ERR << 4)`。

| # | 问题 | 原因 |
|---|---|---|
| 1 | ERR 读不出来 | ESC_ID 低 8 位 ≥ `0x10` 时，ID 与 `ERR<<4` 按位或，ERR 被覆盖且不可逆。手册 P.26 的建议"设置成小于 16，以免与报错类型冲突"正是针对此点 |
| 2 | 速度模式控制帧与大疆冲突 | 速度帧 = `0x200 + ESC_ID`，ESC_ID 为 1~15 时落在 `0x201~0x20F`，命中大疆反馈帧 |

工程现状（由代码推断，电机内实际配置待核对）：ESC_ID ≈ `0xF1 / 0xF2`，低 8 位 ≥ `0x10`，`D[0]` 高半字节恒为 F，ERR 目前一定读不出。MST_ID 为 `0xA1 / 0xA2`。

## 3. 约束与规则

设 ESC_ID 为 `n`，`n = 0x100·h + l`，`l = 1..15`。

- **C1（ERR 可还原）**：`n & 0xFF ∈ [0x01, 0x0F]`。
  ⚠ 两份手册对 D[0] 中 ID 取"低 8 位"还是"低 4 位"表述不一致，但本约束同时满足两种解读，天然规避该歧义。
- **C2（不与已占用 ID 冲突，且 ≤ `0x7FF`）**：

| 来源 | 占用 ID |
|---|---|
| 大疆控制帧 | `0x1FE 0x1FF 0x200 0x2FE 0x2FF` |
| 大疆反馈帧 | `0x201~0x20C`（C6x0 用 `0x200+id`；GM6020 用 `0x205+id`） |
| 瓴控 LK | `0x141~0x148` |
| 工程其他 | `0x66 0x67 0x68 0x77 0x78 0x79 0x89 0xA0 0xA1 0xA2 0xD1~0xD4 0x6FF` |

- **C3（反馈帧不能被其他达妙电机当成指令）**：`MST_ID ≠ n + 0x100·k`。

按 `h` 检查：`h=0` 速度帧撞大疆；`h=1` 位置速度帧撞大疆反馈；`h=2` MIT 帧撞大疆反馈；**`h=3、4` 四种帧全部无冲突**；`h≥5` 力位混控帧超过 `0x7FF`。

### 建议规则（待队内确认）

`l` 为电机在该路 CAN 上的序号，1~15。

| 项目 | 取值 |
|---|---|
| ESC_ID | `0x300 + l` |
| MIT 帧 | `0x300 + l` |
| 位置速度帧 | `0x400 + l` |
| 速度帧 | `0x500 + l` |
| 力位混控帧 | `0x600 + l` |
| MST_ID | `0x700 + l` |

解码：`ID = D[0] & 0x0F`，`ERR = D[0] >> 4`。

备选与说明：
- MST_ID 若要更高仲裁优先级，可用 `0x20 + l`（`0x21~0x2F`，当前无占用）。
- 若只用 MIT + 位置速度模式（不用速度和力位混控），可取 `h=0`：`0x0l` / `0x10l` / MST `0x30 + l`，其余 ID 更保留。
- 本规则与手册 P.26"建议小于 16"的字面值不同，但满足其意图（低 8 位 ≤ `0x0F`）。此为**待实测项**：写入 `0x301` 后抓反馈，确认 `D[0]` 低半字节为 `1`、高半字节为 ERR。

### 3.1 为什么邮箱/掩码解决不了这两个问题

**结论：不能。** 硬件过滤器不改变以下两件事。

过滤器能做的：在 MCU **接收侧**按 **ID** 把帧分流到不同 FIFO，或直接丢弃。H723 的 FDCAN 最多 128 个过滤器、两个 RX FIFO。

| 问题 | 为什么过滤器无效 |
|---|---|
| ERR 读不出 | `D[0] = ID \| ERR<<4` 是**达妙固件**用自己的 ESC_ID 打包写入的。过滤器只决定我们收不收，不改变报文内容。唯一解法仍是让 ESC_ID 低 8 位 ≤ `0x0F` |
| 与大疆帧冲突 | 冲突发生在**达妙电机自己的接收端**：ESC_ID=1 时达妙速度帧 = `0x201`，而大疆 1 号电机反馈也发 `0x201`，达妙会把这帧反馈当成速度指令执行。我们 MCU 的过滤器管不到达妙电机收什么 |
| 同 ID、不同发送者 | 过滤器按 ID 匹配，**不区分发送者**。两帧 ID 相同时，无论 mailbox/mask 怎么配都无法分开 |

过滤器唯一相关的正当用途：把达妙与大疆放到**不同 CAN 总线**。相同 ID 不在同一条线上，自然不会互相干扰。这属于总线隔离，不是过滤器的作用。

工程现状：`CAN_Configure_Reception()` 使用 accept-all（`FilterID1=0, FilterID2=0, FDCAN_FILTER_MASK`），全部进 FIFO0，再在 `tsk_config_and_callback.cpp` 里 `switch(Header.Identifier)` 分发。改为多过滤器分流只能省 ISR 开销，不能解决冲突。

### 3.2 ESC_ID 不设到 0x300 以上的可行条件

取 `h=0`（ESC_ID = `0x01~0x0F`）：

| 项目 | ID | 空闲情况 |
|---|---|---|
| ESC_ID / MIT | `0x0l` | ✓ |
| 位置速度 | `0x10l` | ✓ |
| 速度 | `0x20l` | ✗ `l ≤ 0x0C` 时撞大疆反馈 `0x201~0x20C` |
| 力位混控 | `0x30l` | ✓ |
| MST_ID | `0x40 + l` | ✓ |

条件：

1. **低 8 位仍须 `0x01~0x0F`**——过滤器不能放宽这一条。
2. **不使用速度模式。** 只用 MIT + 位置速度（+力位混控）时，15 个 ID 全部可用。
3. **必须用速度模式时**，只有 `l = 0x0D~0x0F` 可用（速度帧 `0x20D~0x20F` 才避开大疆反馈 `0x201~0x20C`），每路最多 3 台。
4. `MST_ID` 须避开全部达妙控制 ID（`0x0l/0x10l/0x20l/0x30l`）与大疆监听 ID（`0x1FE 0x1FF 0x200 0x2FE 0x2FF`）。`0x40+l` 满足。
5. `l` 取 `0x0D~0x0F` 时 MIT 帧为 `0x0D~0x0F`，同样满足 ERR 可读。

对比 `h=3`（`0x30l` 起）：四种模式全可用、每路 15 台，代价是 ID 高于 `0x300`。二者不可兼得，这是 ID 空间的硬约束，与过滤器无关。

## 4. 当前驱动中的硬编码（只读结论，未改）

| 位置 | 现状 | 问题 |
|---|---|---|
| `Data_Process` 速度/力矩解码 | 量程写死 `±30`、`±10` | Init 传入的 `Omega_Max` 默认 20.94，与 RX 的 ±30 不一致；MIT 收发必须共用同一组 VMAX/TMAX，而 VMAX/TMAX 又是上位机里用户设的，因此**驱动不能写死，必须由调用方传入并同时用于收发两侧** |
| `Data_Process` 角度 | `raw/65536*PI + 1.57` | 与手册映射 `uint_to_float(raw, -PMAX, PMAX, 16)` 不符。PMAX 由用户在上位机设定、不是固定 π，驱动必须按传入的 PMAX 计算；`+1.57` 为历史补偿，需按新口径重写 |
| `Data_Process` 圈数 | `delta_position` 为 `int16_t`，混用度/弧度；`Total_Round` 不参与 `Now_Angle` | 多圈功能不可用。J4310 反馈限 `[-π,π]`，必须做回绕展开才能多圈 |
| 各发送处 | `+0xF0 / +0x1F0 / +0x2F0` 写死 | 换 ID 规则必须改驱动 |
| `TIM_Alive` 末尾 | 无论什么模式，固定向 `ID+0xF0` 补发使能帧 | 手册 P.15 明确指令帧 ID 随模式变化；位置速度/速度模式下的补发 ID 可疑 |
| `Init` / `allocate_tx_data` | 只处理 FDCAN1/2；FDCAN3 返回未初始化指针 | 在 CAN3 用达妙会野指针 |
| `dvc_dmmotor.h` ErrorCode | 缺 0/1/3/4/5 | 失能/使能/校准异常无枚举，无法判读 |
| `drv_can.cpp` | 复位帧发往 `0xF2` | 同上 |
| `tsk_config_and_callback.cpp` | 应用层写死 `0xA1/0xA2` 分发 | 驱动与应用层各存一份 ID 规则 |

## 5. 两类达妙电机与驱动职责

| | 双编码器（J4310-2EC） | 增量式单编码器（S2325-1EC） |
|---|---|---|
| 反馈位置参考 | 输出轴绝对，掉电不丢 | **转子侧**，上电归零，无绝对参考 |
| 驱动现状 | 现有 `Class_DM_Motor_J4310`，解码有问题 | **缺失** |

**驱动职责边界（已确认）：**
- 校准、校准后重设零点**不属于**电机驱动职责。驱动只需按手册格式解析反馈、按模式打包指令。
- 扭矩换算只考虑减速比，不计效率：`τ_out = τ_rotor · N`。
- `N` 作为构造/初始化参数传入，不写死。
- **PMAX/VMAX/TMAX 由用户在上位机设置，不是固件常量。** 驱动必须把三者作为初始化参数，且**收发两侧共用同一组值**，不得在 RX 侧写死。

**单编码器（转子侧）换算：**

- `θ_out = θ_rotor / N`
- `ω_out = ω_rotor / N`
- `τ_out = τ_rotor · N`
- 回绕展开必须基于**转子侧**回绕周期（`2·PMAX`），展开完成后再除以 `N`。若先除以 `N` 再展开，会因输出轴一圈对应转子 `N` 转而丢失圈数。

## 7. 兼容性方案（讨论用，未实施）

目标：驱动更新后，其他兵种现有代码不改也能编译、行为不变。

**拟冻结的对外接口：** 类名 `Class_DM_Motor_J4310`、`Init()` 签名、`Enum_DM_Motor_ID` 取值、`CAN_RxCpltCallback(uint8_t*)`、各 getter 的单位与语义。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 解码档位，默认旧档 | 增加 `Set_Decode_Profile(LEGACY / STANDARD)`，`LEGACY` 保持现有行为 | 其他兵种零改动 | 旧偏方需保留到全部迁移完 |
| B. 新建类，旧类冻结 | 新增 `Class_DM_Motor_DualEncoder` / `SingleEncoder`，旧类标注弃用 | 边界清晰；增量式可独立设计 | 两套并存 |
| C. 编译宏 | `#ifdef DM_LEGACY_DECODE` | 实现最简 | 同一驱动在不同兵种行为不同，不推荐 |
| D. 原地直接修复 | 全队同步升级 | 最干净 | 违背"不影响其他兵种" |

**倾向：两个独立类，不引入继承**
- `Class_DM_Motor_J4310` 的类名、成员函数签名、公有接口保持不变。
- 新增 `Class_DM_Motor_S2325` 承载增量式单编码器，独立成类，不继承。
- 位布局解析抽成 `.cpp` 内的 `static` 自由函数，两个类共同调用，避免位域写两遍。
- ID 规则做成可配置基址，默认值等价于现有 `0xF0` 偏移与 `0xA0` 基址；驱动提供 `Get_MST_ID()` 供应用层分发，应用层不再手写 `0xA1`。
- PMAX/VMAX/TMAX 与减速比一并作为初始化参数，不设默认硬编码；旧档为兼容保留原写死值。

### 7.1 设计原则（后续所有改动都受此约束）

1. **不擅自改代码。** 任何改动先经队内确认，再动。
2. **不改既有类的结构、函数签名、命名。** 新增一律追加，不改既有。
3. **必须能在没有 AI 的情况下维护和排错。** 由此推出：
   - 不引入继承/虚函数（会加 vptr、改对象内存布局，且把行为藏进动态派发）
   - 不用编译宏切换行为（同一份驱动在不同兵种表现不同，读代码看不出来）
   - 不写"聪明"的抽象；宁可显式重复，也不要隐式耦合
   - 每个量都注明单位、量程、来源（上位机配置 / 固件常量 / 实测）
4. **修 bug 与改行为分开。** 修 bug 可以原地改；改行为必须走 ID 规则那套讨论流程。

### 7.2 类结构（讨论用，未实施）

```
Class_DM_Motor_J4310     // 双编码器，反馈=输出轴。名字、结构、接口全部不动
Class_DM_Motor_S2325     // 增量式单编码器，反馈=转子侧，独立新类
```

**按 7.1 原则，放弃共同父类的原因：**

| 做法 | 被否决的理由 |
|---|---|
| 抽象父类 + 虚函数 | 改既有类的内存布局（vptr）；对象若被 `memcpy`/按布局序列化会出错；虚派发让"读一个 .cpp 就能看懂"变难 |
| 编译宏切解码 | 同一驱动在不同兵种行为不同，且编译器看不到的分支最容易藏 bug |
| 共用基类只放数据成员 | 既有类的成员顺序会变，等于改了结构 |

**共享位布局的做法：**

在 `dvc_dmmotor.cpp` 内用 `static` 自由函数（不进头文件、不改任何类）：

| 函数 | 职责 |
|---|---|
| `DM_Parse_Feedback(D[8], out)` | `D[0]` 拆 ID/ERR；`POS` 16bit、`VEL` 12bit、`T` 12bit、`T_MOS`、`T_Rotor`。两份手册位域一致 |
| `DM_Pack_MIT(...)` | MIT 帧 8 字节布局 |
| `DM_Pack_PosVel(...)` / `DM_Pack_Vel(...)` | 位置速度 / 速度帧布局 |
| `DM_Command_Enable/Disable/Clear/SaveZero()` | `0xFF...FC/FD/FB/FE`，两机型一致 |

两个类各自调用这些函数，位域只在**一处**定义。改协议只需改这一处，不会出现"改了一个类忘了另一个"。

**代价（明确承认）：**

- 两个类仍有重复：PID 对象、命中检测、Target/Out、各 getter。这部分不值得抽，重复反而好读。
- 若将来第三种达妙电机出现，重复会变多。届时再考虑抽象，现在不预支复杂度。

**`Class_DM_Motor_S2325` 与 J4310 的实质差异：**

| | J4310 | S2325 |
|---|---|---|
| 反馈换算 | 恒等（固件已输出输出轴数据） | `θ/N`、`ω/N`、`τ·N` |
| 控制量换算 | 恒等 | `θ·N`、`ω·N`、`τ/N` |
| 绝对参考 | 有 | 无（上电归零） |
| 回绕展开 | 按 `2·PMAX` | 按 `2·PMAX`，**在转子侧展开后再除以 N** |

**两个方向的换算必须成对实现。** 只做反馈侧除法会导致"给定 30°、读回 1.2°"，两边各自看都正常，极难发现。建议在类里写一句注释说明配对关系。
